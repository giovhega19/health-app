# ADR-006 · Zustand + TanStack Query para el estado del cliente

- **Estado:** Propuesto
- **Fecha:** 2026-09-22
- **Relacionado:** `04-arquitectura.md` §2, RNF-02, F01-F09

## Contexto
La app móvil necesita gestionar dos tipos de estado claramente distintos: estado de UI/vista (por ejemplo, el paso actual del onboarding, si un modal está abierto, el estado local del cronómetro mientras se lee del `TimerEngine`) y estado de servidor (datos que van y vuelven del backend a través del cliente HTTP generado por contrato, ver ADR-004: catálogo, manifiesto, feature flags). RNF-02 exige arranque en frío < 2,5 s y animaciones a 60 fps, por lo que la librería de estado no debe introducir renders innecesarios ni boilerplate que complique mantener ese rendimiento. Además, Art. 4 (offline-first) establece que el dispositivo es la fuente de verdad de los datos de entrenamiento en el MVP: las escrituras de dominio (rutinas, programación, sesiones) no pasan por una caché de estado de servidor sino por el `SyncEngine` y el outbox descritos en ADR-002.

## Opciones consideradas
1. **Redux + Redux Toolkit (RTK):** maduro, con herramientas de depuración extensas.
   - Pros: ecosistema grande, patrones bien conocidos.
   - Contras: boilerplate considerable (slices, selectores, thunks) para un equipo pequeño; RTK Query solaparía innecesariamente con el cliente HTTP ya generado por contrato (ADR-004); más código a mantener sin beneficio claro frente a las necesidades reales de FitApp.
2. **Context + `useReducer` nativo de React:** sin dependencias externas.
   - Pros: cero librerías nuevas.
   - Contras: rendimiento pobre a escala si no se particiona con cuidado (re-renders de árboles completos de componentes), lo que pone en riesgo RNF-02 (60 fps); no resuelve por sí solo la caché, reintentos ni invalidación del estado de servidor, obligando a reconstruir a mano lo que TanStack Query ya ofrece.
3. **Zustand para el estado de UI (view-models) + TanStack Query para el estado de servidor**, construido sobre el cliente HTTP tipado generado por contrato (ADR-004).
   - Pros: Zustand es mínimo, sin boilerplate, con stores fáciles de probar de forma aislada (coherente con Art. 3); TanStack Query resuelve caché, reintentos, invalidación y estados de carga/error del estado de servidor sin código adicional; ambas librerías están ya listadas como stack aprobado en `04-arquitectura.md` §2, evitando introducir herramientas nuevas sin justificación.
   - Contras: dos librerías en vez de una sola solución integral; requiere disciplina para no mezclar responsabilidades (un store de Zustand no debe re-implementar lo que ya hace TanStack Query, y viceversa).

## Decisión
Se adopta **Zustand** para los view-models de presentación (estado de UI local a cada feature, p. ej. el store que expone el estado del `TimerEngine` a la pantalla de sesión) y **TanStack Query** para el estado de servidor de solo lectura obtenido a través del cliente HTTP generado por contrato (ADR-004): catálogo de ejercicios/rutinas, manifiesto de versión, feature flags remotos y cualquier otra consulta `GET` contra el backend.

Se deja **explícito** que **TanStack Query no gestiona las escrituras offline-first** de los datos de entrenamiento del usuario (perfil, rutinas, programación, sesiones, progreso, gamificación): esas escrituras se realizan a través de los repositorios locales (SQLite/Drizzle) y se sincronizan mediante la tabla `outbox` y el `SyncEngine` descritos en ADR-002. TanStack Query se limita a datos de servidor de solo lectura o de baja frecuencia de escritura que no forman parte del flujo offline-first crítico (p. ej. `/catalog/manifest`, `/config/flags`).

## Consecuencias
**Positivas**
- Zustand mantiene los stores de presentación simples y fácilmente probables de forma aislada con Jest/RNTL, sin boilerplate.
- TanStack Query cubre caché, reintentos y estados de carga/error del estado de servidor sin reconstruir esa lógica a mano, contribuyendo a RNF-02.
- La separación explícita de responsabilidades (Zustand = UI, TanStack Query = servidor de solo lectura, outbox/SyncEngine = escrituras offline-first) evita ambigüedad sobre dónde vive cada tipo de estado en cada Fxx.

**Negativas / a vigilar**
- Cada plan técnico de Fxx debe indicar explícitamente, para cada pieza de estado nueva, si es un store de Zustand, una query de TanStack Query, o una escritura vía outbox, para evitar que se mezclen responsabilidades.
- Si en el futuro aparece la necesidad real de sincronizar estado complejo entre muchos stores de Zustand, se revisará si sigue siendo suficiente o si se requiere una herramienta adicional (nuevo ADR).
