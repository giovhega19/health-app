# ADR-005 · TimerEngine puro con marcas de tiempo absolutas

- **Estado:** Propuesto
- **Fecha:** 2026-09-22
- **Relacionado:** RF-05.02, RNF-03, RNF-12, RN-05, F05

## Contexto
RF-05.02 exige un motor de temporizador con fases (preparación, trabajo, descanso entre series, descanso entre ejercicios, descanso entre rondas y completado), todas parametrizables según RN-05. RNF-03 exige que la desviación del cronómetro sea ≤ 1 s en una sesión de 60 minutos, incluso tras pasar a segundo plano o bloquear el dispositivo, y establece explícitamente que el tiempo **nunca** debe calcularse acumulando ticks. RNF-12 exige que el temporizador no use GPS ni sondeos de red, que se actualice en pantalla a ≤ 4 Hz y que se suspenda en segundo plano (para no drenar batería). El sistema operativo puede pausar o limitar la ejecución de JavaScript en segundo plano, por lo que cualquier mecanismo basado en `setInterval`/acumulación de ticks pierde precisión de forma acumulativa.

## Opciones consideradas
1. **Acumular ticks** (un `setInterval` que resta un segundo en cada disparo mientras la app está en primer plano): simple de implementar.
   - Pros: trivial de escribir inicialmente.
   - Contras: viola RNF-03 de forma directa (la desviación crece con cada tick perdido, especialmente en segundo plano o cuando el hilo de JS se retrasa); el propio requerimiento prohíbe explícitamente esta estrategia.
2. **Delegar a alarmas nativas del sistema operativo** (usar temporizadores/alarmas nativas de iOS/Android en vez de lógica propia en JS): podría dar precisión nativa.
   - Pros: no depende del hilo de JS para medir el tiempo.
   - Contras: acopla el dominio de la sesión de entrenamiento a APIs nativas específicas de plataforma, violando Art. 2.2 (el dominio no puede depender de Expo/frameworks nativos); complica las pruebas unitarias deterministas del motor (no se puede probar con un reloj falso de forma sencilla); mayor complejidad de mantenimiento para un beneficio que las marcas de tiempo absolutas ya cubren.
3. **Motor de temporizador puro basado en marcas de tiempo absolutas** (`TimerEngine` en `workout-session/domain`): una máquina de estados determinista que, dado `startedAt`, la configuración de fases (RN-05) y una marca `now` (inyectada vía el puerto `Clock`), calcula la fase y el tiempo restante actuales sin acumular nada; al recalcular siempre se usa `now - startedAt` (menos pausas acumuladas), de modo que un retraso puntual del hilo de JS no se arrastra. Al pasar a segundo plano se programan notificaciones locales (vía un puerto de notificaciones) para el fin de cada intervalo pendiente; al volver a primer plano, el estado se recalcula desde cero con `now` actual.
   - Pros: cumple RNF-03 por diseño (el error no se acumula, se recalcula siempre contra el instante absoluto); 100 % probable con un `Clock` falso en pruebas unitarias de dominio (Art. 2.4); la actualización en pantalla puede limitarse a ≤ 4 Hz (RNF-12) sin afectar la precisión real del cálculo, porque la UI solo lee el estado, no lo produce.
   - Contras: exige diseñar con cuidado la máquina de estados de fases y la interacción con el puerto de notificaciones al pasar a segundo plano.

## Decisión
Se adopta un **`TimerEngine` puro** en `workout-session/domain/TimerEngine.ts`: una función/máquina de estados determinista que recibe la configuración de fases (RN-05), el instante de inicio (`startedAt`), las pausas acumuladas y un `now` (obtenido del puerto `Clock`, nunca de `Date.now()` directo en el dominio) y devuelve la fase y el tiempo restante actuales. La UI (presentation) solo lee este estado a una frecuencia ≤ 4 Hz (RNF-12); no lo calcula. Al pasar a segundo plano, un caso de uso de aplicación programa notificaciones locales para el fin de cada intervalo pendiente a través de un puerto de notificaciones; al volver a primer plano, el estado se recalcula íntegramente a partir de `startedAt` y las pausas, nunca por acumulación de ticks.

## Consecuencias
**Positivas**
- Cumple RNF-03 por construcción: el cálculo siempre parte de marcas de tiempo absolutas, así que un retraso puntual no se acumula.
- El `TimerEngine` es una función pura del dominio, 100 % cubierta por pruebas unitarias con `Clock` falso, coherente con Art. 2.4 y Art. 3.2 (cobertura de dominio ≥ 90 %).
- Compatible con RNF-12 (batería): la frecuencia de refresco de UI es independiente de la precisión del cálculo subyacente.

**Negativas / a vigilar**
- Requiere que el puerto `Clock` y el puerto de notificaciones estén bien definidos antes de implementar F05 (se detallará en el plan técnico de F05); ningún adaptador de infraestructura debe filtrarse al dominio del `TimerEngine`.
- Las pausas y reanudaciones deben registrarse con cuidado (tiempo acumulado de pausa) para que el recálculo tras segundo plano sea exacto; se verificará con pruebas de propiedad (fast-check) en el plan técnico de F05.
